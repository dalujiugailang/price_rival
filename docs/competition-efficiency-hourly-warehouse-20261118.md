# 京东换新小时数仓

2026-11-18：用户确认替代原按整天划分覆盖期的口径。

- 来源：用户上传京东换新Excel。首行字段为报价日期、报价小时、商品型号、A等级价位段、报价量、提交量。
- A等级价位段等同提交A等级价位段（统一），不再访问本地操盘DuckDB作为本页的小时数据源。
- 报价小时为北京时间小时起点，15代表15:00至16:00。
- 价格生效边界：可靠快照保存时刻向上取整至整点，精确整点保持不变。例如15:37→16:00，15:58→16:00，23:59→次日00:00。
- 覆盖期为[本次生效整点, 下一次生效整点)，不重叠；同一生效整点采用最后保存版本，同一天不同整点仍保留各期。
- 恢复导入记录没有可验证的原保存时刻，不能将导入时间当作生效时刻；不纳入小时分析。汇总快照可界定下一次切换边界，其自身不能计算分组。
- 新品活动仍沿用保存次日起3个自然日的规则，仅在相交常规期整期排除相应型号，不作永久排除。

## 累计与替换

独立SQLite位于主业务数据库同目录下的`competition-efficiency/hourly-warehouse.sqlite`，与业务快照表分开。Docker现有data挂载可持久化此文件。

### 一张明细表与统一查询入口

不是DuckDB。物理明细只存于`hourly`表，包含所有上传版本；查询当前正式数据使用`fact_jd_tradein_quote_hourly`视图，自动关联日期当前版本。不要直接对`hourly`全表求和，否则会混入已替换版本。

| 视图字段 | 含义 |
| --- | --- |
| channel | 固定京东换新 |
| quote_date | 报价日期 |
| quote_hour | 报价小时，0—23 |
| quote_time | 小时起点，带北京时间+08:00 |
| model | 原始商品型号 |
| submission_a_price_band | 提交A等级价位段 |
| quote_count | 报价量 |
| submission_count | 提交量 |
| source_import_id | 来源上传版本 |

`imports`保存来源文件与哈希，`active_days`指定每天当前有效版本，`day_versions`记录替换历史；它们是管理表，不是另拆的经营明细。

```sql
SELECT quote_date, SUM(quote_count) quotes, SUM(submission_count) submissions
FROM fact_jd_tradein_quote_hourly
GROUP BY quote_date ORDER BY quote_date;
```

小时区间可直接筛选`quote_time >= '2026-11-01T16:00:00+08:00' AND quote_time < '2026-11-03T16:00:00+08:00'`。所有时间串均采用统一格式和时区。

数仓保存全部历史，页面近两个月的分析窗口不会移除历史数据。导入脚本为`node ops/import_efficiency_hourly.mjs [--replace-dates] 文件...`；重叠日期必须显式指定替换，回执保存到同目录`import-receipt-*.json`。

明细键为日期×小时×规范化型号×价位段，文件内重复键拒绝入仓。单次文件可含多个完整日期。界面预览新旧按日汇总，并要求确认全天完整、包含竞争与非竞争型号。今天及未来日期拒绝入仓。

新增日期累计；重叠日期经确认后整日切换到新版本，不作加法。原始Excel、旧明细及日期版本均保留。相同文件哈希不重复累计；预览revision防止并发上传覆盖未审阅的新版本。一天内缺少某小时记录可以是无报价，因此以用户确认全天导出作为日期完整性依据；缺少整天数据的覆盖期明确排除，不补零。

## 分析

以最新入仓日期为锚点，取近两个月完整覆盖期。分层Y仍按每期竞争组实际报价量计算权重，提交率按汇总提交量/报价量，不平均小时提交率。型号规范化保留原型号值，只做NFKC、去空白及大小写归一。

上传入仓后立即重读小时数仓和共享快照并计算；刷新共享历史时也重新请求分析。小时数据存在后不混用旧日粒度数据及模型。小时历史尚未齐备时显示缺失原因；模型需要在新口径样本上另行重新拟合。

API：GET `/api/competition-efficiency/warehouse`，POST同路径的`/preview`、`/import`，GET `/api/competition-efficiency`。读取需要竞争投入效率页面权限；写入还需要editor/admin。沿用登录与同源校验。
